# Concepts — Development

The host obtains an access token from its external issuer. It sends advertised suites to `POST /v1/challenges`. Capabilities are advisory; a challenge selects exactly one suite. StrongBox is preferred before TEE. Generation never retries with a different suite; request another policy decision from the server if the selected suite is unavailable.

For registration, `HardwareKeys.generate` creates a fresh P-256 signing key with the decoded nonce as its attestation challenge, BIOMETRIC_STRONG authentication for each operation and invalidation on enrollment change. Private keys remain in Android Keystore. The local key security level must exactly match the selected suite. The host exports the leaf-first DER chain and signs the registration statement after authentication. The server derives keyId as lowercase SHA-256 of the leaf SubjectPublicKeyInfo DER and validates the attestation independently. Local checks do not replace server trust validation.

For signing, the host hashes the exact document (maximum 512 KiB), obtains a challenge for the registered key and document digest, reconstructs the statement with the trusted issuer/subject and compares it with the server-returned statement. Only matching bytes reach `BiometricSigner.sign`. The host then submits the original document and the resulting DER signature. Biometric approval authenticates use of the key; the host must show the document and obtain meaningful approval separately.

The statement contains nine UTF-8 fields: `sworn-ink/v1`, operation, suite, challengeId, padded base64 nonce, issuer, subject, keyId, documentSHA256. Each field has an unsigned 32-bit big-endian byte-length prefix. Registration uses an empty documentSHA256. `SHA256withECDSA` hashes the statement once inside the signing operation. No prehash API is offered, avoiding confusion with double-hashed documents.

`HardwareKeys` calls block and belong on a host worker executor. `BiometricSigner` belongs to a single FragmentActivity and all of its methods/callbacks run on the main thread. It holds only one pending operation. `onStop` cancels the operation; `onDestroy` closes the signer. Rotation/backgrounding therefore requires a fresh explicit attempt. Nothing automatically resumes or signs after a lifecycle change. The host owns transport retries, token expiry, challenge expiry and persistence of its alias-to-account binding.
